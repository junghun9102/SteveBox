# report

대화 중 나온 내용(기술 개발 계획, 조사 결과, 회고, 현황 정리 등)을 다른 사람에게 공유할 수 있는 독립 HTML 페이지로 만듭니다. 코드를 만드는 게 아니라 **읽는 사람 입장에서 이해하기 쉬운 문서**를 만드는 작업이라는 걸 염두에 두세요.

이 스킬은 Claude Code 클라우드 세션(claude.ai/code)과 로컬 세션 모두에서 동작합니다. 경로는 모두 **저장소 루트 기준 상대경로**입니다.

## 왜 이런 순서로 진행하는가

리포트는 한 번 잘못 만들면 다시 쓰는 비용이 큽니다(HTML 스타일링까지 다 갈아엎어야 함). 그래서 **내용이 확정되기 전까지는 HTML을 만들지 않습니다.** 순서: 모호한 점 질문 → 텍스트 초안 확인 → (확정되면) HTML 생성 → (요청 시) 공유.

## 1단계 — 내용 파악 및 질문

전달받은 내용만으로 리포트를 채우기에 애매하거나 빠진 부분이 있으면 먼저 질문합니다. 예를 들어:

- 리포트의 목적/대상 독자가 불명확한 경우 (예: 팀 공유용인지, 의사결정 요청용인지)
- 일정, 담당자, 범위처럼 구체적인 사실 정보가 필요한데 언급되지 않은 경우
- 대화 맥락만으로는 결론/권장사항이 뭔지 애매한 경우

이미 대화에서 충분히 설명된 내용이면 다시 묻지 말고 바로 진행하세요. 리포트 품질을 위해 꼭 필요한 것만 확인합니다.

## 2단계 — 텍스트 초안으로 먼저 확인받기

**HTML을 만들기 전에 반드시 채팅에 마크다운 형태로 초안을 먼저 보여주고 확인을 받습니다.** 이 단계를 건너뛰지 마세요 — 톤이나 구조를 바꿀 때 마크다운을 고치는 게 HTML을 고치는 것보다 훨씬 빠릅니다.

### 섹션 구성은 가이드일 뿐, 강제 템플릿이 아님

아래 섹션들은 참고용 체크리스트입니다. 주제에 맞게 필요한 것만 쓰고, 안 맞으면 빼거나 이름을 바꾸거나 새로 만드세요.

- 배경 / 문제 정의
- 목표
- 범위 (하는 것 / 안 하는 것)
- 상세 계획 또는 진행 내용 (단계별)
- 일정
- 리스크 및 고려사항
- 참고 링크 (이슈, 문서, PR 등)

회고, 조사 결과, 현황 공유 등은 이 목록에 얽매이지 말고 내용에 맞는 구조로 자유롭게 짜세요.

### 구조/관계를 설명하는 내용이면 다이어그램을 계획하세요

모듈 의존 관계, 아키텍처, 데이터 흐름처럼 "관계"가 들어간다면 문장으로 설명하고 끝내지 마세요. 초안 단계에서 "여기는 다이어그램이 필요하다"를 판단해두면 HTML을 두 번 만들 필요가 없습니다. 방법은 `references/diagrams.md` 참고 — 정적 SVG부터 인터랙티브 그래프(Cytoscape.js)까지 예시가 있습니다.

초안을 보여준 뒤 물어보세요: 그대로 HTML로 만들지, 수정할 부분이 있는지.

### 공개 저장소에 올라간다는 점을 확인하세요

이 리포트는 개인 GitHub 저장소와 GitHub Pages로 공개될 수 있습니다. 초안에 회사 내부 정보(사내 코드, 내부 이슈/위키 내용, 사내 URL·IP, 고객 정보, 토큰·키 등)가 들어 있으면 HTML을 만들기 전에 사용자에게 알리고 제거하거나 일반화할지 확인하세요.

## 3단계 — HTML 리포트 생성

사용자가 초안을 확정하면 진행합니다.

**저장 위치**: `report/` (저장소 루트 기준)
**파일명 규칙**: `YYYY-MM-DD-영문-slug.html` (오늘 날짜 + 제목을 kebab-case 영문 슬러그로). 예: `report/2026-09-01-flipper-release-guard-review.html`

1. `.claude/skills/report/assets/template.html`을 참고해서 새 파일을 작성합니다. 구조와 CSS 클래스(`report-header`, `meta`, `tags`/`tag`, `callout` 등)는 그대로 재사용하고, `report/style.css`를 상대경로(`./style.css`)로 링크하세요 — 매 리포트마다 스타일을 새로 만들지 않기 위함입니다.
2. 확정된 마크다운 초안을 HTML로 옮깁니다. 표, 코드블록, 리스트는 `style.css`가 이미 스타일링하므로 시맨틱 태그(`<table>`, `<pre><code>`, `<ul>` 등)만 쓰면 됩니다.
   - 리스크/주의사항: `<div class="callout risk">`(또는 `info`/`success`)
   - 모듈명·상태값 같은 짧은 라벨 나열: `<span class="pill">`
   - 다이어그램·범례·코드 뭉치처럼 본문과 분리된 덩어리: `<div class="card">` (넓으면 `<div class="card scroll">`)
   - 앞서 계획한 다이어그램은 이 단계에서 실제로 그립니다. 데이터가 코드/설정 파일에 있으면 그걸 실제로 읽어서 노드/엣지를 채우세요 — 손으로 나열한 다이어그램은 틀리기 쉽습니다.
3. `report/index.html`의 `<!-- REPORT_LIST_START -->` ~ `<!-- REPORT_LIST_END -->` 사이 목록 **맨 위**에 새 항목을 추가합니다:
   ```html
   <li><a href="./2026-09-01-flipper-release-guard-review.html"><span class="title">리포트 제목</span><span class="date">2026-09-01</span></a></li>
   ```
4. 만든 파일 경로를 사용자에게 알려줍니다. 로컬 세션이면 브라우저로 열어서 보여줄 수 있습니다.

## 4단계 — 공유 (요청 시에만 진행)

파일 생성까지는 다시 묻지 않고 진행하되, **git commit/push는 자동으로 하지 않습니다.** 사용자가 "올려줘", "공유해줘", "깃허브에 올려줘" 등으로 명시적으로 요청할 때만 진행하세요.

```bash
git status
git add report/<새-파일>.html report/index.html   # add -A / add . 금지
git commit -m "리포트: <제목>"
git push -u origin HEAD
```

- 커밋은 현재 체크아웃된 브랜치에 합니다. 클라우드 세션은 보통 세션용 작업 브랜치에서 시작합니다.
- 현재 브랜치가 GitHub Pages 배포 브랜치(기본 `main`)가 아니면, push한 뒤 `main` 으로 가는 PR을 만들고 그 링크를 알려주세요. 머지는 사용자가 합니다.
- force push, 다른 브랜치 삭제/리셋은 하지 않습니다.
- GitHub Pages가 아직 켜져 있지 않다면, 저장소 Settings → Pages에서 Source를 `main` 브랜치(`/ (root)`)로 설정하도록 사용자에게 안내하세요. 이 설정은 Claude가 대신하지 않습니다. 켜진 뒤 주소는 `https://<사용자명>.github.io/<저장소명>/report/` 형태입니다.
- 무료 플랜에서 GitHub Pages는 공개(public) 저장소에서만 동작합니다. 비공개 저장소면 사용자에게 알려주세요.

## 안전 가이드

- HTML을 만들기 전 텍스트 초안 확인 단계를 생략하지 마세요.
- 회사 내부 정보나 민감정보가 공개 저장소에 올라가지 않게 하세요 (2단계 참고).
- `report/style.css`는 모든 리포트가 공유하는 파일입니다. 특정 리포트만을 위해 기존 규칙을 고치지 말고, 필요한 스타일은 그 리포트 파일 안에 `<style>`로 추가하세요.
- git add는 이번에 만든 파일만 명시적으로 지정하고, `git add -A` / `git add .`는 쓰지 마세요.
- 저장소 설정(GitHub Pages 등) 변경은 사용자가 직접 하도록 안내하세요.
